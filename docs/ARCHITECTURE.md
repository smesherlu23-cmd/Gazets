# Архитектура: чем рисуется полоса

ТЗ (раздел 2) просит явно выбрать один из двух путей рендера полосы и
обосновать выбор. Выбран **первый: HTML/CSS под капотом, Flet — только
оболочка редактора.**

## Решение

Полоса собирается в HTML (`pechatnya/render/html.py`) и рендерится headless-
Chromium (`pechatnya/render/engine.py`). Готовый PNG показывается в окне Flet
как картинка, поверх которой интерфейс кладёт прозрачные слои взаимодействия.
Экспорт PNG и PDF идёт тем же движком, поэтому выгруженный файл в точности
повторяет превью.

## Почему не канвас Flet

Газетная полоса — это не набор прямоугольников, а типографика:

| Что нужно по ТЗ | В CSS | На канвасе Flet |
|---|---|---|
| Перетекание текста по колонкам (п. 4.4) | `column-count` | свой алгоритм разбиения на строки и колонки |
| Выключка по ширине и переносы | `text-align: justify`, `hyphens: auto` | своя расстановка пробелов и словарь переносов |
| Буквица в обтекание | `float: left` | ручной обсчёт обтекания абзаца |
| Фото и врезки, не рвущиеся по колонкам | `break-inside: avoid` | ручной контроль разрывов |
| Слой состаривания (п. 4.6) | `mix-blend-mode: multiply` поверх градиентов | сборка растра в PIL и наложение |
| PDF для печати (п. 4.7) | печать страницы браузером | свой генератор PDF |

На канвасе каждый пункт пришлось бы писать руками, причём качество набора
(межсловные пробелы в выключке, переносы, висячие строки) — именно то, за счёт
чего результат похож на настоящую газету, а не на «текст в рамках».

Плата за выбор — зависимость от браузерного движка. Она смягчена тем, что
движок ищется в трёх местах (см. README) и на Windows 10/11 всегда есть Edge.

## Как это работает

```
модель проекта ──► render/html.py ──► HTML одной полосы
                                        │
                        render/engine.py (служебный поток)
                                        │
                     ┌──────────────────┼──────────────────┐
                 PNG превью        метрики блоков       PNG/PDF экспорт
                     │                  │                    │
              ui/preview.py      проценты заполнения    render/export.py
                     │           и координаты блоков
              ui/screen_layout.py: картинка + прозрачные слои
```

### Служебный поток движка

Синхронный API Playwright нельзя вызывать из потока, где крутится asyncio-цикл
Flet. Поэтому браузер живёт в отдельном потоке, а превью, экспорт и замер
ставят туда задачи через очередь (`ChromiumEngine._submit`). Побочная польза —
одна страница браузера переиспользуется, и пересборка превью укладывается в
0,3–0,6 с на выпуск из десяти статей.

### Замер вместимости

Многоколоночный текст при переполнении уходит не вниз, а вбок — в лишние
колонки, поэтому `scrollHeight` ничего не скажет. Блок меряется по клону в одну
колонку нужной ширины: высота содержимого, делённая на «высота блока × число
колонок», даёт непрерывный процент заполнения, а из него — остаток в знаках
(`MEASURE_JS` в `render/engine.py`). Тот же проход возвращает координаты блоков
на листе.

### Сетка полосы — дерево

Полоса хранится деревом узлов (`Frame`): узел либо делит место между детьми в
ряд или в колонку, либо несёт блок. Размер задаётся весом (доля свободного
места) или числом пикселей. Такая модель прямо ложится на вложенные flex-блоки
в HTML, а операции конструктора становятся правкой одного-двух узлов: деление —
это подстановка контейнера с двумя листьями, удаление — выбрасывание листа с
последующим схлопыванием контейнера, перестановка — обмен соседей.

Плоские строки прошлой версии (`rows[] → blocks[]`) читаются и переводятся в
дерево при открытии файла (`migrate_project_dict`), поэтому старые выпуски
открываются как есть.

Ручки границ рисуются между соседями внутри контейнера, поэтому замер отдаёт
не только блоки с процентом заполнения, но и прямоугольники самих узлов:
`MEASURE_JS` собирает `[data-frame]` и `[data-block]` за один проход.

### Лист и поля

Размер листа считается из формата и ориентации (`Project.sheet_px`), поля — из
миллиметров (`margins_px`). Метрики набора подобраны под A4 при 96 dpi
(794 × 1123 px); на другом формате текста просто помещается больше или меньше.
Размер листа проходит насквозь: окно браузера при рендере, ширина превью,
разрешение PNG и физический размер страницы PDF.

### Перенос остатка на другую полосу

Сколько знаков влезет в блок, формулой не посчитать: мешают переносы, врезки и
балансировка колонок. Поэтому точка разрыва подбирается замерами
(`render/split.py`): первый замер переполнения даёт оценку, дальше — двоичный
поиск по длине первой части, каждая проба это рендер полосы и замер блока.
Оценка сужает интервал, поэтому обычно хватает трёх-четырёх проб — около
полусекунды. Разрыв двигается к ближайшему пробелу, чтобы не разорвать слово.

Статья при этом остаётся одна: в модели у блока появляется `article_part`, а у
статьи — `split_at`. Первая часть печатает лид, автора, снимок и строку
«продолжение на стр. N», вторая — уменьшенный заголовок и «начало на стр. M».
Правка текста меняет обе части сразу, а кнопка «убрать перенос» возвращает
статью в один блок.

### Взаимодействие поверх картинки

Интерфейс не перерисовывает HTML ради выделения: по координатам из замера над
картинкой раскладываются прозрачные зоны — клик выделяет блок, двойной клик
открывает редактор статьи, `DragTarget` принимает статью из левого списка, а
узкие полоски на стыках блоков тянут границы (меняют веса блоков и строк в
модели). Пересборка HTML нужна только когда изменилась сама полоса.

### Пересборка превью

Правки текста не запускают рендер на каждый символ: `ui/preview.py` копит
запросы и рисует последний через ~400 мс паузы. Структурные изменения
(перетаскивание, смена шаблона, переключение полосы) просят немедленный
рендер.

## Единицы измерения

Лист — 794 × 1123 CSS-пикселя при 96 dpi (пропорция A4/A3, поля 34 × 38 px):
в этих числах заданы все метрики набора из дизайн-пакета. Физический формат
влияет только на экспорт: PNG масштабируется через `dpi / 96`, PDF печатается
листом A4 или A3.

### Отмена действий

История — снимки проекта в JSON (`AppState`): перед каждой правкой прошлое
состояние уходит в стопку отмены, правки подряд в пределах 1,2 секунды
складываются в один шаг, чтобы отмена не стала посимвольной. Глубина — 60
шагов. Смена проекта историю обнуляет: отменить «назад в предыдущий выпуск»
нельзя.

## Формат проекта и наследование облика

Один JSON (`<имя>.pechatnya.json`) + папка `<имя>.images` рядом. Чтение
устойчиво к версиям: незнакомые поля игнорируются, отсутствующие берутся из
значений по умолчанию (`pechatnya/serde.py`), так что старый проект открывается
новой версией приложения.

Картинки при сохранении собираются в папку проекта и записываются
относительными путями (`storage.relocate_images`). Это важно в двух случаях:
снимок вставили до первого сохранения (он лежал в профиле по абсолютному пути)
и выпуск сохранили в другое место — иначе файл уехал бы без картинок.

Издания живут отдельно от выпусков — в `publications.json` в профиле
пользователя. Выпуск хранит `publication_id` **и** снимок оформления. Снимок
нужен, чтобы файл проекта открывался на машине, где библиотеки нет: тогда
газета выглядит так же, как при сохранении. Если издание в библиотеке найдено,
при открытии проекта оформление берётся из него — поэтому правка логотипа или
шрифтов видна сразу во всех номерах этого издания, а вёрстка и тексты остаются
в файле выпуска и не затрагиваются (`Project.inherit`).
